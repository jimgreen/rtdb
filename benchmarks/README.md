# RTDB 基准测试

`benchmark_core.py` 使用当前公开的 `Table` 接口，对固定数据规模测试：

- 单行条件查询；
- 热键读取和 `get_many()` 冷/热缓存读取；
- 主键两字段投影的冷/热缓存读取；
- 500 个独立 key 命令的 Redis 风格只读 pipeline；
- 与 pipeline 相同请求量的逐 key 读取对照；
- 单行条件修改；
- 多条条件修改的一次 WAL 提交；
- 显式 `Table.transaction()` 主键写批；
- 非主键等值条件的单行局部修改；
- 批量新增；
- 4 进程并发追加；
- 4 进程批量追加（每进程一次 `insert_many`）；
- 8 线程混合读写。

从仓库根目录运行：

```powershell
python benchmarks\benchmark_core.py --json
```

结果中的 `seconds` 是一次完整工作负载的耗时。比较优化前后时，应使用
相同 Python 版本、相同磁盘和相同参数；加速比计算为：

```text
优化前耗时 / 优化后耗时
```

本轮固定表 WAL 实验使用同一台 Windows 主机、50,000 条初始记录和相同
的 `benchmark_core.py` 工作负载。基线是每次提交执行 WAL `fsync` 和表文件
`fsync`；候选版本保留 CRC32 和 generation 校验，但采用 WAL 先落盘、4 MiB
阈值 checkpoint，并在 WAL 已被当前 generation 覆盖时只检查尾帧。为降低磁盘
调度噪声，写入和并发项目各重复三次，表中使用中位数：

| 场景 | 基线（秒） | 候选（秒） | 加速比 |
| --- | ---: | ---: | ---: |
| 主键单行更新 | 0.1819 | 0.1508 | 1.21x |
| key-value 单行更新 | 0.1834 | 0.1464 | 1.25x |
| 独立条件更新（300 次） | 2.9911 | 2.0615 | 1.45x |
| 非主键等值局部更新（100 次） | 0.7643 | 0.5927 | 1.29x |
| 多进程逐条追加（4×25） | 4.4953 | 4.4143 | 1.02x |
| 多线程混合读写 | 0.3921 | 0.2920 | 1.34x |

批量路径本来已经共用一个 WAL frame，候选版本的变化在测量误差范围内；因此
没有用批量项目的偶然小波动作为采用依据。公开基准最近一次完整运行仍应结合
磁盘负载重复执行，尤其是多进程项目。

在上述 WAL 候选版本上继续加入“主键持久索引定点探针”后，使用同一组
50,000 条记录、相同参数重复运行。该改动只影响冷主键定位：完整索引仍保留
为回退路径，探针先校验 CRC/generation，再复用编码主键槽位图。与加入探针
前的当前版本相比，代表性中位数如下（多进程和线程项目的波动应以本机多次
运行结果为准）：

| 场景 | 加入探针前（秒） | 加入探针后（秒） | 加速比 |
| --- | ---: | ---: | ---: |
| 持久化索引首次主键读取 | 0.0772 | 0.0548 | 1.41x |
| 主键单行更新 | 0.1442 | 0.1215 | 1.19x |
| key-value 单行更新 | 0.1501 | 0.1214 | 1.24x |
| 500 个独立 key 读取 | 0.1907 | 0.1672 | 1.14x |
| 多线程混合读写 | 0.3382 | 0.3371 | 1.00x |

前四项是探针直接覆盖的冷/热点主键路径，达到保留条件。多进程追加不经过
主键定点探针，仍采用前一张 WAL 对比表的 4×25 进程基准；它的波动主要来自
进程启动、Windows 文件锁和磁盘调度。多线程项目启用并发自适应：线程数较多
时走一次共享的完整索引构建，避免每个 worker 串行解析探针，因此没有保留
初版候选出现的明显线程回退。

本轮继续采用 Redis/AOF 风格的“数据文件权威、索引可丢弃”边界，复用进程内
侧索引写句柄，并缓存已经校验过的索引描述符。句柄在侧文件原子替换前显式
失效；WAL、记录 CRC、generation 发布顺序、跨进程文件锁和热同步语义均未改变。
本轮开始时先用同一工作区版本复现了一次基线；候选版本在相同的 50,000 条
初始记录、4 进程/8 线程参数下连续运行三次并取中位数。由于基线只复现一次，
下表用于判断优化方向，不能替代同一磁盘负载下的严格 A/B 中位数实验：

| 场景 | 修改前（秒） | 句柄/描述符复用后（秒） | 加速比 |
| --- | ---: | ---: | ---: |
| 主键单行更新 | 0.1273 | 0.1119 | 1.14x |
| key-value 单行更新 | 0.1206 | 0.1131 | 1.07x |
| 非主键等值局部更新（100 次） | 0.5135 | 0.3869 | 1.33x |
| 多进程逐条追加（4×25） | 4.5906 | 4.3454 | 1.06x |
| 多线程混合读写 | 0.3475 | 0.2637 | 1.32x |

多进程项目受 Windows 进程启动、文件锁竞争和磁盘调度影响较大，表中只把
三次中位数作为方向性证据；没有取消每条写的 WAL `fsync`，也没有把侧索引
写入错误升级成数据提交失败。若需要更高写入吞吐，应优先使用已有的
`insert_many`、`update_many_where`、key-value `update_many` 或
`table.transaction()`，让多个变更共享一个 WAL frame 和一次耐久同步。

本轮继续优化 value-only 提交：只推进当前进程已经加载的持久化索引，未使用
的 sidecar 保持可丢弃的旧 generation；主键 probe 的 generation 头复用一个
无缓冲句柄。这样不会改变表文件/WAL 的权威性，也不会取消任何 `fsync`、CRC、
generation 或跨进程锁。一个 20 次主键单行更新的 `cProfile` 对比显示，索引
维护从约 23 ms 降到约 5 ms，剩余主要耗时是 20 次 WAL `fsync` 约 49 ms。

后续又把“插入时为主键唯一性临时构建的索引”与“实际服务过查询或更新的热索引”
区分开来。只有后者会参与 value-only generation 推进，避免仅追加后从未读取的
表在第一次单行写入时维护无关 primary sidecar；结构性增删仍走完整 sidecar
目录校验和增量 delta 路径。

在同一台 Windows 主机、50,000 条初始记录、4 进程/8 线程参数下，本轮完整基准
连续运行三次取中位数如下。上表的“加入 probe sidecar 后”作为本轮前的参照；
多进程和多线程项目的变化没有被当作本轮加速结论：

| 场景 | 本轮前参照（秒） | 本轮后中位数（秒） | 加速比 |
| --- | ---: | ---: | ---: |
| 主键单行更新 | 0.0666 | 0.0566 | 1.18x |
| key-value 单行更新 | 0.0650 | 0.0558 | 1.17x |
| 非主键等值局部更新（100 次） | 未单独复现 | 0.3735 | — |
| 多进程逐条追加（4×25） | 3.6410 | 4.3001 | 不宣称加速 |
| 多进程批量追加（4×25） | 0.4830 | 0.4866 | 约 0.99x |
| 多线程混合读写 | 0.2720 | 0.2728 | 约 1.00x |

单行更新的改善来自索引维护系统调用减少；多进程追加仍由进程启动、文件锁
竞争和磁盘调度主导，批量接口仍是安全吞吐路径。不同磁盘负载下应重复运行
基准后再做部署判断。

本轮继续加入固定宽度主键 probe sidecar：sidecar 使用冗余 header、generation、
布局校验和 payload CRC；排序后的编码主键和槽位可以直接二分定位，结构性
变更追加固定宽度 delta，单行追加不额外写 sidecar，以保持最热追加路径的
并发效率。数据表和 WAL 仍是唯一权威来源。与上一轮“侧索引句柄/描述符复用”
版本相比，在相同 50,000 条初始记录、4 进程/8 线程参数下连续三次取中位数：

| 场景 | 加入 probe sidecar 前（秒） | 加入后（秒） | 加速比 |
| --- | ---: | ---: | ---: |
| 持久化索引首次主键读取 | 0.0574 | 0.0008 | 73.5x |
| 主键单行更新 | 0.1119 | 0.0666 | 1.68x |
| key-value 单行更新 | 0.1131 | 0.0650 | 1.74x |
| 多进程逐条追加（4×25） | 4.3454 | 3.6410 | 1.19x |
| 多进程批量追加（4×25） | 约 0.48 | 0.4830 | 约 1.00x |
| 多线程混合读写 | 0.2637 | 0.2720 | 0.97x |

主键冷定位、单行更新和多进程逐条追加达到保留条件；多线程混合读写的中位数
略有波动，未把它宣称为加速，且没有改变 WAL `fsync`、CRC、generation、
跨进程锁或热同步语义。若业务以单条追加为主，sidecar 允许暂时落后一代，
下次访问会经过 generation 检查并安全回退到普通索引；多行结构变更仍会增量
维护 sidecar，并在 delta 达到 512 KiB 后压缩为新的有序基表。

## Redis 与文件映射后端对比

Redis 后端使用 `core/redis_db.py`，基准脚本为：

```powershell
python -m pip install -r core\requirements-redis.txt
python benchmarks\benchmark_redis_vs_file.py --rows 50000 --repeat 3 `
  --redis-url redis://127.0.0.1:6390/0 --durability always `
  --output output\redis-comparison-50000.json
```

需先启动指定地址的 Redis 服务。可使用 `--json` 在终端输出完整 JSON；
`--output` 保存环境、原始运行数据、中位数、最终记录数和内容摘要。
脚本对两个后端执行相同工作负载，每轮交替先后顺序，并核对完整最终数据。
每个项目的比值定义为：

```text
file/redis = median(file_mapped_seconds) / median(redis_seconds)
```

大于 1 表示 Redis 更快，小于 1 表示文件映射更快。连接失败、服务端配置不符
或工作负载/数据校验失败时，脚本会报错并停止，不生成不完整的加速比。

默认 `--durability always` 校验以下配置，不会自动修改服务器：

```text
appendonly yes
appendfsync always
no-appendfsync-on-rewrite no
maxmemory-policy noeviction
```

文件映射后端每个独立写提交都执行 WAL `fsync`，Redis 使用 AOF `always`。
二者的恢复机制不同，但本次对比没有通过降低 Redis 的持久化等级换取吞吐。
`--durability server` 接受服务器当前策略，仅适用于明确接受该策略的实验；
`everysec` 或关闭 AOF 的结果不能与下表混为一谈。`WAIT` 可以增加副本确认，
但它不等于副本磁盘同步；本次单机基准没有配置复制等待。

2026-10-28 实测环境：Windows 10.0.26200、Python 3.11.15、redis-py 8.1.0、
Redis 8.10.3（Windows MSYS2 便携运行时）、本机 TCP。每轮从 50,000 条记录
开始，连续三轮取中位数；表中时间是整组操作总耗时，不是每条记录耗时。
原始结果保存在 `output/redis-comparison-50000.json`（`output/` 不纳入 Git）。

| 场景与操作量 | 文件映射（秒） | Redis（秒） | file/redis |
| --- | ---: | ---: | ---: |
| 初始 50,000 条写入，每批 1,000 条 | 1.122934 | 6.549818 | 0.171x |
| 同一主键读取 300 次（预热后） | 0.003547 | 0.049970 | 0.071x |
| 主键单行更新 20 次 | 0.055406 | 0.058242 | 0.951x |
| key-value 单行更新 20 次 | 0.051130 | 0.056867 | 0.899x |
| 非主键等值局部更新 50 次 | 0.122865 | 0.143784 | 0.855x |
| 500 条批量读取，重复 20 次 | 0.013696 | 0.319813 | 0.043x |
| 500 命令读取 pipeline，重复 20 次 | 0.015215 | 0.344813 | 0.044x |
| 500 条 key-value 批量更新 | 0.011338 | 0.041748 | 0.272x |
| 500 个条件一次批量更新 | 0.011607 | 0.036791 | 0.315x |
| 显式事务更新 500 条 | 0.012141 | 0.045963 | 0.264x |
| 2,000 条批量追加 | 0.041673 | 0.232866 | 0.179x |
| 8 线程，每线程读取 60 次并追加 5 条 | 0.199479 | 0.146578 | **1.361x** |
| 4 进程，每进程逐条追加 25 条 | 3.124866 | 0.395965 | **7.892x** |
| 4 进程，每进程一批追加 25 条 | 0.545498 | 0.220530 | **2.474x** |
| 单行删除 20 次 | 0.411949 | 0.058340 | **7.061x** |
| 500 条批量删除 | 0.007654 | 0.034232 | 0.224x |

六次后端运行均得到 51,720 条最终记录，逐条内容与预期一致；两种后端的
SHA-256 内容摘要也一致：

```text
6185eb672e3dea5728a5285c123bcd196d2d85784560fa18b12fbf8c392acb38
```

Redis 在本组多进程追加、线程混合读写和单行删除中占优；文件映射在本地点读
和多数批量操作中占优。文件映射热读会复用进程内缓存，Redis 每次仍有本机
TCP、Lua 和 MessagePack 开销；Redis 为各字段维护服务端索引，也增加写入
成本。因此保留两个可选后端，没有据此把默认文件映射内核整体替换为 Redis。

多进程耗时包含 Windows `spawn`、连接/开表与退出，不能解读为稳态吞吐或
单次 Redis 命令延迟。线程测试使用追加写入；它不代表所有更新型混合负载。
三次中位数没有覆盖更多机器、网络部署或长期压力运行，部署前应以实际字段数、
记录规模和持久化配置复测。

针对 Lua 等值候选选择和深分页又做了一组独立的 Redis A/B 测试。脚本把旧的
候选选择器冻结为基线，保持 Redis 版本、AOF、数据、序列化和 Python API 不变：

```powershell
python benchmarks\benchmark_redis_queries.py `
  --redis-server output\redis-runtime\Redis-8.10.3-Windows-x64-msys2\redis-server.exe `
  --repeat 3 --calls 20 --tests `
  --output output\redis-query-comparison.json
```

每个场景每轮执行 20 次，表中 50,000 条记录；时间是该场景 20 次调用总和，
`before/after` 是旧/当前实现，倍率为 `before / after`：

| 场景 | before（秒） | after（秒） | 加速比 |
| --- | ---: | ---: | ---: |
| 多条件，首条命中，`LIMIT 1` | 0.136914 | 0.005344 | **25.62x** |
| 多条件，匹配在后部，`LIMIT 1` | 2.266205 | 0.498021 | **4.55x** |
| 多条件空交集 | 4.569997 | 0.115752 | **39.48x** |
| 多条件稠密结果，`LIMIT 1` | 0.169498 | 0.004670 | **36.30x** |
| 多条件 `OFFSET 1000 LIMIT 20` | 2.467153 | 0.660585 | **3.73x** |
| 普通顺序 `OFFSET 40000 LIMIT 1` | 7.410220 | 0.004970 | **1490.93x** |
| 单字段等值 `OFFSET 20000 LIMIT 1` | 3.637358 | 0.004177 | **870.81x** |
| 单字段等值尾部 `OFFSET 24980` | 4.580818 | 0.011068 | **413.86x** |

多条件查询使用“最多检查 128 个最小候选”的快速路径；窗口填不满时才调用
Redis `ZINTER`，避免首条命中被完整交集操作拖慢。深分页直接从 sorted set 的
目标 rank 读取，跳过的记录不再加载或解包。主键过滤和单字段首条读取作为对照
路径，早先/本次结果约 0.97--1.39x，整组仅几毫秒；这类调度噪声不作为提速结论。
此 A/B 结果保存在 `output/redis-query-comparison.json`，脚本还输出两个 Lua
版本文件，便于复核基线与当前实现的摘要。

曾尝试无条件采用 `ZINTER`，但首条命中和稠密结果的 `LIMIT 1` 分别降到原来
速度的约 0.36x、0.20x，因此没有采用。原始实验保存在
`output/redis-intersection-unconditional-rejected.json`。最终保留的是上表的
自适应版本；批次内已有暂存修改时仍使用原有可见性规则，无上限查询保留原
扫描路径。深分页的大倍率来自消除数万条无用记录解码，不能外推到普通点查。

当前版本在独立 Redis 服务上完成全部 73 项回归（含 20 项真实 Redis 集成测试
及 1 项公开异常导出测试），覆盖分页、物理重排、联合主键、索引更新、批量
失败原子性、线程读写和跨客户端可见性。基准和回归结束后临时服务 key 数为 0；
进程随后退出。AOF 强制终止恢复和跨进程热同步由下述独立脚本验证通过。

真实 Redis 回归与进程崩溃恢复验证命令：

```powershell
$env:RTDB_TEST_REDIS_URL = "redis://127.0.0.1:6390/0"
python -m unittest core.test_redis_db core.test_file_mapped_db core.test_table_schema web.test_server -q
python benchmarks\verify_redis_durability.py `
  --redis-server output\redis-runtime\Redis-8.10.3-Windows-x64-msys2\redis-server.exe `
  --output output\redis-durability.json
```

未设置 `RTDB_TEST_REDIS_URL` 时，真实 Redis 集成用例会被跳过，不能把跳过
当成 Redis 验证通过。恢复脚本启动独立临时服务，确认另一进程的修改能被已
打开的表直接读取，然后强制终止 Redis，通过 AOF 重启核对全部记录、更新、
删除及等值索引。实测全部 100 条预期记录恢复一致；结果文件为
`output/redis-durability.json`。该结果只证明进程终止与 AOF 重启恢复，不包含
物理掉电、磁盘故障或文件系统损坏。脚本仅清理自己创建的临时 namespace，
不执行 `FLUSHDB`，不修改共享服务器配置。

## SQLite、文件映射、Redis 三后端对比

SQLite 后端使用 `core/sqlite_db.py`，文件映射后端使用 `core/file_mapped_db.py`，
Redis 后端使用 `core/redis_db.py`。统一基准脚本为：

```powershell
python benchmarks\benchmark_three_backends.py `
  --redis-server output\redis-runtime\Redis-8.10.3-Windows-x64-msys2\redis-server.exe `
  --rows 50000 --repeat 3 `
  --output output\three-backends-50000-rerun.json
```

本次复测使用同一台 Windows 主机、Python 3.11.15、SQLite 3.53.1、Redis 8.10.3，
Redis AOF `appendfsync always`，50,000 条初始记录。三个后端每轮使用独立临时目录，
执行顺序轮换，运行三轮取中位数。SQLite 使用 WAL、`synchronous=FULL` 和
`mmap_size=256 MiB`；文件映射使用现有 WAL/CRC/generation；Redis 使用 AOF always、
`noeviction`。每轮核对最终记录、记录数和 SHA-256；三者摘要均为：

```text
79e2507672df7edea9eb3cf5e30d6b1ee53c0cd85012ec9399ee05bd6ffa21f1
```

表中时间是整个场景的总耗时，操作次数已经写入场景名称。

| 场景 | 文件映射 | Redis | SQLite | 最快 |
| --- | ---: | ---: | ---: | --- |

| 非主键等值更新 50 次 | 0.128012s | 0.137034s | **0.119102s** | SQLite |

| 单行删除 20 次 | 0.410580s | 0.054456s | **0.043858s** | SQLite |
| 批量删除 500 条 | **0.007742s** | 0.034862s | 0.008116s | 文件映射 |

复测显示没有一个后端在所有场景都最快：

- **文件映射**：本机同进程主键点读、批量读、pipeline 读、批量追加和批量删除最强。
  它直接操作固定格式 mmap，避免了网络和通用 SQL 层开销，适合低延迟、固定结构、
  单机本地访问。代价是等值索引、WAL 和跨进程锁由本系统维护，单行删除和多进程逐条
  写入不如 Redis/SQLite。
- **SQLite**：本次 19 个场景中单条/条件更新、批量更新、事务更新、删除和初始装载
  多数最快。它提供成熟 SQL、事务、索引和清晰的多进程文件语义，适合作为默认通用
  后端，尤其适合需要复杂条件、多个表和可审计事务的本机应用。
- **Redis**：本机 TCP 场景下，多线程混合读写、4 进程逐条追加和批量追加最快。它有
  独立服务进程、天然跨进程/跨主机共享、Lua/命令原子性和成熟的复制/哨兵/集群能力；
  代价是网络协议、序列化、内存占用和 AOF/恢复运维成本。AOF always 下它仍不一定胜过
  SQLite 的单行写入。

推荐按工作负载选择：

1. 需要标准 SQL、复杂条件查询、多张表、事务和本机多进程写入：**优先 SQLite**。
2. 需要极低本机点读/批量读、固定记录格式、可接受本项目专用 API：**优先文件映射**。
3. 需要多个服务或多台机器共享、集中协调、水平扩展、发布订阅或 Redis 原子脚本：
   **优先 Redis**。
4. 主要是多进程逐条写入文件映射表：可以启用 `FileMappedWriteProcess` 集中提交；
   但单生产者逐条写和同进程多线程共享表仍使用原直接接口。集中写入的专项结果见
   `output/file-mapped-writer-final-50000.json`。

本次结果不是延迟上限或跨机器结论。Redis 测试使用本机 TCP 和 AOF always；如果改用
`appendfsync everysec`，吞吐通常会提高但安全语义不同，不能与本表直接等价。SQLite 和
文件映射均使用 FULL/WAL 安全路径。完整原始数据保存在
`output/three-backends-50000-rerun.json`，其中包含每轮耗时、执行顺序、环境和验证信息。

## SQLite 专用写进程基准

`benchmark_sqlite_writer.py` 对比原来的多进程直接写入与
`SQLiteWriteProcess` 集中写入。两者均使用 `WAL + synchronous=FULL`，
每次从相同的 50,000 条数据开始，计时截止到所有写入都收到提交确认。
每轮逐行核对预期内容、SHA-256 摘要和 `PRAGMA integrity_check`。
集中路径使用一个本机 IPC 写进程、每组最多 256 个请求、1 ms 合并窗口。

实测环境：Windows 10.0.26200，Python 3.11.15，SQLite 3.53.1。
以下为 2026-10-28 三轮中位数；加速比为直接写耗时 / 集中写耗时。

| 场景与操作量 | 直接写（秒） | 集中写（秒） | 加速比 | 集中事务数 |
| --- | ---: | ---: | ---: | ---: |
| 4 进程各逐条追加 250 条，共 1,000 条 | 3.0453 | **1.0187** | **2.99x** | 250–251 |
| 4 进程各逐条主键更新 250 条，共 1,000 条 | 3.8945 | **1.0195** | **3.82x** | 250–251 |
| 4 进程各逐条主键删除 250 条，共 1,000 条 | 3.4293 | **1.0432** | **3.29x** | 250 |
| 4 进程各一次批量追加 250 条，共 1,000 条 | **0.0516** | 0.0569 | 0.91x | 1 |
| 4 进程各一次批量更新 250 条，共 1,000 条 | 0.0495 | **0.0214** | **2.31x** | 1 |
| 8 线程各 250 次更新、500 次读取，共 2,000 写 / 4,000 读 | 8.1376 | **1.0582** | **7.69x** | 250–252 |
| 单生产者逐条追加 100 条 | **0.2267** | 0.4058 | 0.56x | 100 |

每轮交替执行顺序。以上时间是完整工作负载的总耗时，包含 IPC、排队、SQLite
提交和结果返回；**不包含进程启动、连接预热和退出**。JSON 另外记录
`setup_seconds` 与 `teardown_seconds`，适合评估常驻写进程，不能把这些加速比
套用到每次只写几行就重启服务的场景。种子数据装载与结果验证也不参与计时。
首次访问集中写进程中的表发生在计时内，包含其一次 schema 校验。

逐条并发路径将 1,000 次独立事务合并为约 250 次；8 线程路径将 2,000 次合并为
约 250 次。`stats.commits` 是分组事务计数，不包含建表事务，也不是底层真实
fsync 系统调用计数。各轮完整数据与直接写模式一致，摘要随不同场景变化。

两项退化也保留在报告中：已经使用 `insert_many` 的大批量追加，中间的 IPC 和
校验调度成本可能超过节省的提交成本；单生产者同步逐条写无法形成跨请求合并。
因此集中写是可选路径，原直写路径仍适用于这两类负载。测试存在磁盘调度长尾，
例如集中批量更新某轮为 0.6315 秒，另两轮为 0.0198、0.0214 秒；本表取中位数，
并未删除异常轮次。这组结果是本机工作负载测量，不是延迟上限保证。

初版实验还发现 Windows/Python 3.11 的 `Queue.get(timeout=0.001)` 和
`time.monotonic()` 分别受定时等待粒度及 15.625 ms 时钟精度影响，导致收集窗口
被放大。最终使用 `perf_counter()` 截止时间及短 `sleep()` 让出执行，保留 FULL
提交后确认。未采用的两版原始数据分别保存在
`output/sqlite-writer-rejected-timeout-50000.json` 与
`output/sqlite-writer-rejected-clock-50000.json`。

```powershell
python benchmarks\benchmark_sqlite_writer.py `
  --rows 50000 --repeat 3 `
  --output output\sqlite-writer-50000.json
```

最终原始数据在 `output/sqlite-writer-50000.json`，包含每轮耗时、环境、SQLite
配置、提交计数、启动/退出时间和内容摘要。`output/` 不纳入 Git。

## 文件映射版集中写入基准

`benchmark_file_mapped_writer.py` 在相同 50,000 条种子数据上比较直接 CRUD 与
`FileMappedWriteProcess`。WAL、CRC、文件锁和 mmap 格式保持不变；每轮从临时目录
里的独立数据库开始，完整核对实际记录、预期记录、SHA-256，再重新打开核对全部记录。

2026-10-28 最终代码复测，Windows/Python 3.11.15，4 进程各 50 次写入，三轮中位数。
线程场景为 8 线程共享同一个表对象，每线程 50 次更新、100 次读取。
加速比为直接写耗时 / 集中写耗时。

| 场景 | 直接写（秒） | 集中写（秒） | 加速比 | 集中 WAL 提交数 |
| --- | ---: | ---: | ---: | ---: |
| 4 进程逐条追加 200 条 | 9.9233 | 0.3700 | 26.82x | 50 |
| 4 进程主键单行更新 200 条 | 0.8026 | 0.2980 | 2.69x | 50 |
| 4 进程 key-value 更新 200 条 | 0.8030 | 0.3009 | 2.67x | 50 |
| 4 进程非主键等值更新 200 条 | 3.6499 | 0.4607 | 7.92x | 50 |
| 4 进程单行删除 200 条 | 8.6794 | 0.3729 | 23.27x | 50 |
| 4 进程各批量追加 50 条 | 0.3605 | 0.1072 | 3.36x | 1 |
| 4 进程各批量更新 50 条 | 0.3682 | 0.0991 | 3.71x | 1 |
| 8 线程共享表，400 写 + 800 读 | 1.2438 | 13.8398 | 0.09x | 105–123 |
| 单生产者逐条追加 50 条 | 0.2982 | 0.3543 | 0.84x | 50 |

集中写将 200 次独立 WAL 事务合并成 50 次；4 个显式批量请求合并成一次。
提交次数不是总 fsync 系统调用数，收益还包括减少跨进程索引刷新和文件锁切换。
两条路径都保留 WAL 持久化确认，没有降低同步强度。

**单生产者和共享表的线程混合读写继续推荐原直接接口。** 单生产者逐条追加慢约
18.8%；8 线程混合读写慢约 11.13 倍。集中写进程在另一进程发布 generation，使读线程
频繁重新校验自己的缓存；同进程直接写入可以保留热缓存。集中写因此保持为可选的
多进程写入接口，没有自动替换 SQL、列表访问或普通 CRUD。线程集中路径三轮为
22.208 / 13.840 / 9.638 秒，波动明显，报告保留全部轮次。

计时包括首轮索引加载、IPC、排队、WAL fsync 和返回确认，不包括种子装载、进程
启动/连接、退出和结果校验。启动/退出成本分别保存在 JSON 的 `setup_seconds` /
`teardown_seconds` 中。执行顺序交替安排。这些是本机指定工作负载的吞吐测量，
不能用作单请求延迟保证，也不适用于每次只写几行就重启服务的用法。

最终原始结果为 `output/file-mapped-writer-final-50000.json`，包括三轮耗时、环境、
参数、提交次数、完整内容摘要和受测源文件 SHA-256。先前探索数据仍保留：
`output/file-mapped-writer-50000.json` 为较早一轮多进程结果；
`output/file-mapped-writer-threads-50000.json` 为 8 线程每线程 25 次更新的共享表结果；
`output/file-mapped-writer-pilot.json` 为每线程独立打开表的初始试跑。这些探索结果
不替代上表的最终复测结果。`output/` 不纳入 Git。

```powershell
python benchmarks/benchmark_file_mapped_writer.py --rows 50000 --writes 50 --repeat 3 `
  --output output/file-mapped-writer-final-50000.json
```
